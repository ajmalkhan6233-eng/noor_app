# noor (نور) — Cloud Developer Master Prompt

**Status:** New — this document didn't exist before; it's the handoff
prompt for Claude Code, written 5 August 2026.

**How to use this:** paste the block below (between the `---` lines)
directly into Claude Code as one message. It follows the same
separate-commits pattern that worked for you before (light theme /
dashboard / qibla landed successfully that way) — Claude Code should not
batch everything into one commit.

---

```
Work in THREE SEPARATE COMMITS on the noor repo (Android only, ignore iOS).
After each commit: run flutter analyze and flutter test, then commit and
push before starting the next one. Do not batch all three into one commit.

COMMIT 1 — Fix app_colors.dart palette regression
lib/core/constants/app_colors.dart currently has the OLD dark emerald
values (background 0xFF0A1912, gold 0xFFD4AF37). This is wrong — it
regressed the palette that was already shipped and confirmed working in
build 18. Replace it with the correct shipped light palette:
  paper #F2EFE7 (background), card #FFFFFF, ink #16211C (primary text),
  sage #6E7B72 (secondary text), hairline #E3DFD4 (1px borders),
  emerald #14603C (accent/active), gold #B8912F (Allah calligraphy only).
Set surfaceTintColor to Colors.transparent everywhere so Material 3 does
not tint surfaces green. Search the whole lib/ tree for any remaining
hardcoded dark-emerald hex values or old AppColors references and fix
those too, not just the constants file. Do not touch the haptic glow /
BackdropFilter glass treatment on the Tasbih counter — that logic is
independent of the palette and should stay.

COMMIT 2 — Resolve the three release blockers
1. android/app/src/main/AndroidManifest.xml: confirm/remove the INTERNET
   permission entirely. It must not be present, requested, or merged in
   from any plugin manifest.
2. Same manifest: set android:allowBackup="false" explicitly on the
   <application> tag.
3. lib/core/database/database_helper.dart: replace the hardcoded
   placeholder passphrase with one read from Android Keystore-backed
   secure storage (flutter_secure_storage backed by Keystore is fine).
   Generate a random passphrase on first run if none exists, store it via
   secure storage, never log it, never hardcode it anywhere.
Report back plainly if any of these three can't be fully completed rather
than partially solving and calling it done.

COMMIT 3 — Verify and build
Run flutter analyze and flutter test. Then run a release build. Confirm in
the build summary that:
  - The three blockers from Commit 2 are actually reflected in the built
    APK (permission absent, allowBackup false, passphrase not hardcoded).
  - The palette fix from Commit 1 is visually correct (light theme, no
    dark green remaining).
This build is still debug-signed — that's expected, release signing with a
real keystore is a separate task, not part of this prompt. Push the final
commit and confirm the GitHub Actions run is green.
```

---

## Notes for whoever runs this next

- This prompt intentionally does **not** ask Claude Code to set up release
  signing (real keystore) — that needs a keystore file and passwords
  supplied by you directly, not generated by an AI, and should be its own
  step.
- If Commit 2's Keystore-backed passphrase work turns out to need a plugin
  not already in `pubspec.yaml` (e.g. `flutter_secure_storage`), that's
  expected — it should be added as part of the commit, not treated as a
  blocker to stop and ask about.
- After this lands, remaining release prerequisites are: real release
  signing, Play Store developer account, and a privacy policy (see
  07_QA_SECURITY_AND_RELEASE.md, section 6).
